    Preface

    前言¶

    你可能想知道我们是谁，以及为什么写了这本书。

    在 Harry 的上一本书《Test-Driven Development with Python》（O'Reilly 出版）的结尾，他提出了一些关于架构的问题，比如：如何以易于测试的方式构建应用程序？更具体地说，如何确保核心业务逻辑被单元测试覆盖，同时尽量减少集成测试和端到端测试的数量？他模糊地提到了“六边形架构”、“端口与适配器”和“功能核心，命令式外壳”等概念，但老实说，他并不真正理解这些，也没有在实践中应用过。

    后来，他幸运地遇到了 Bob，Bob对这些问题都有答案。

    Bob 成为一名软件架构师是因为团队中没有人做这件事。虽然他一开始并不擅长，但幸运的是，他遇到了 Ian Cooper，后者教会了他新的编码和思考方式。

    管理复杂性，解决业务问题¶

    我们都在 MADE.com 工作，这是一家欧洲的在线家具销售公司。在那里，我们应用本书中的技术来构建分布式系统，以解决现实世界的业务问题。我们的示例领域是 Bob 为 MADE 构建的第一个系统，而这本书是我们为新加入团队的开发人员编写的教材。

    MADE.com 运营着一个全球供应链，涉及货运合作伙伴和制造商。为了降低成本，我们努力优化库存交付到仓库的时间，避免积压未售出的商品。

    理想情况下，你想要的沙发会在你决定购买的那天到港，我们会直接送货上门，而不需要存储。当货物需要三个月才能通过集装箱船到达时，时间安排是一个棘手的平衡问题。在这个过程中，货物可能会损坏、遭遇风暴延误、物流合作伙伴处理不当、文件丢失、客户改变主意修改订单等等。

    我们通过构建智能软件来解决这些问题，这些软件代表了现实世界中的操作，以便尽可能多地自动化业务流程。

    为什么选择 Python？¶

    如果你正在阅读这本书，我们可能不需要说服你 Python 很棒，所以真正的问题是“为什么 Python 社区需要这样一本书？”答案与 Python 的流行和成熟度有关：尽管 Python 可能是世界上增长最快的编程语言，并且接近绝对流行度的顶端，但它才刚刚开始解决 C# 和 Java 世界多年来一直在处理的问题。初创公司成长为真正的企业；Web 应用和脚本自动化正在成为（小声说）企业软件。

    在 Python 世界中，我们经常引用“Python 之禅”：“应该有一种——最好只有一种——显而易见的方法来做到它。”不幸的是，随着项目规模的扩大，最明显的方法并不总是能帮助你管理复杂性和不断变化的需求。

    我们在本书中讨论的技术和模式都不是新的，但它们大多对 Python 世界来说是新的。这本书并不是 Eric Evans 的《领域驱动设计》或 Martin Fowler 的《企业应用架构模式》（均由 Addison-Wesley Professional 出版）等经典著作的替代品——我们经常引用并鼓励你去阅读。

    但所有这些经典代码示例通常都是用 Java 或 C++/# 编写的，如果你是一个 Python 开发者，并且很久没有使用这些语言（或者从未使用过），这些代码清单可能会让你感到……头疼。这就是为什么 Fowler 的另一本经典著作《重构》（Addison-Wesley Professional 出版）的最新版是用 JavaScript 编写的。

    TDD、DDD 和事件驱动架构¶

    按知名度排序，我们知道的三种管理复杂性的工具是：

    1. 测试驱动开发（TDD）：帮助我们构建正确的代码，并让我们能够重构或添加新功能，而不用担心回归问题。但如何充分利用测试是一个挑战：如何确保测试尽可能快地运行？如何通过快速、无依赖的单元测试获得最大的覆盖率和反馈，同时尽量减少缓慢、不稳定的端到端测试？
    2. 领域驱动设计（DDD）：要求我们专注于构建业务领域的良好模型，但如何确保模型不受基础设施问题的拖累，并且不会变得难以更改？
    3. 松散耦合的（微）服务通过消息集成（有时称为响应式微服务）：是管理跨多个应用程序或业务领域的复杂性的成熟解决方案。但如何让它们与 Python 世界的现有工具（如 Flask、Django、Celery 等）配合使用并不总是显而易见。

    🤔注意: 如果你不从事（或不感兴趣）微服务，请不要被吓到。我们讨论的大多数模式，包括事件驱动架构的大部分内容，完全适用于单体架构。

    本书的目标是介绍几种经典的架构模式，并展示它们如何支持 TDD、DDD 和事件驱动服务。我们希望它能成为在 Python 中实现这些模式的参考，并作为进一步研究的起点。

    适合的读者¶

    我们对亲爱的读者有以下几点假设：

    • 你接触过一些相当复杂的 Python 应用程序。
    • 你经历过管理这种复杂性带来的痛苦。
    • 你可能对 DDD 或任何经典的应用架构模式一无所知。

    我们围绕一个示例应用程序展开对架构模式的探索，逐章构建它。我们在工作中使用 TDD，因此通常会先展示测试列表，然后是实现。如果你不习惯测试优先的工作方式，一开始可能会觉得有点奇怪，但我们希望你很快就能习惯在“看到代码如何构建”之前“看到代码如何使用”。

    我们使用了一些特定的 Python 框架和技术，包括 Flask、SQLAlchemy 和 pytest，以及 Docker 和 Redis。如果你已经熟悉它们，那当然更好，但我们认为这不是必需的。本书的主要目标之一是构建一种架构，使具体的技术选择成为次要的实现细节。

    简要概述你将学到的内容¶

    本书分为两部分，以下是我们将涵盖的主题及其所在的章节。

    第一部分¶
    • 领域建模和 DDD（第 1、2 和 7 章）：在某种程度上，每个人都学到了复杂业务问题需要在代码中反映为一个领域模型的教训。但为什么总是很难做到这一点而不被基础设施问题、Web 框架或其他东西拖累？在第一章中，我们概述了领域建模和 DDD，并展示了如何从一个没有外部依赖的模型开始，以及快速的单元测试。后来，我们回到 DDD 模式，讨论如何选择正确的聚合，以及这种选择如何与数据完整性问题相关。
    • 仓库、服务层和工作单元模式（第 2、4 和 5 章）：在这三章中，我们介绍了三个密切相关且相互支持的模式，以实现我们的目标：让模型摆脱无关的依赖。我们围绕持久存储构建了一个抽象层，并构建了一个服务层来定义系统的入口点并捕获主要用例。我们展示了这一层如何轻松构建系统的薄入口点，无论是 Flask API 还是 CLI。
    • 关于测试和抽象的一些思考（第 3 和 5 章）：在介绍了第一个抽象（仓库模式）之后，我们借此机会讨论了如何选择抽象，以及它们在软件耦合中的作用。在介绍了服务层模式之后，我们谈到了实现测试金字塔和在尽可能高的抽象级别编写单元测试。
    第二部分¶
    • 事件驱动架构（第 8-11 章）：我们介绍了另外三个相互支持的模式：领域事件、消息总线和处理器模式。领域事件是捕获系统交互触发其他交互的一种方式。我们使用消息总线让操作触发事件并调用适当的处理器。接着，我们讨论了如何将事件用作微服务架构中服务集成的模式。
    • 命令查询职责分离（第 12 章）：我们展示了命令查询职责分离的示例，包括使用和不使用事件的情况。
    • 依赖注入（第 13 章）：我们整理了显式和隐式依赖，并实现了一个简单的依赖注入框架。
